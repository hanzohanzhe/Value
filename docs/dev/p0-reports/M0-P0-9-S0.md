## 4 偏差（Deviations）

1. **market-visibility 不是 1/1。** 计划 S0 的验收写的是 market-visibility 1/1，本次任务说明允许它在 M2 之前只因 R3-01 的价格断言失败。我按审查报告 R3-01 的修改建议 (d) 修了 spec：
   - mock 改用 API 真实发送的字段 `price_gbp_per_mwh`，取值 61.25 起，不与任何报价重复，并补上 `price_aggregation` 和 `period_hours`；
   - 新增一条 soft 断言，范围限定在 `.selected-period-strip`。
   - 结果：该 spec 目前 0/1，失败只有这一条 soft 断言，其余断言（merit order、VRE 页、axe 扫描）全部执行并通过。这一点由 `error_must_match` 强制：任何不匹配的错误都让棘轮失败。最初的正则只钉住了“哪条断言”，没有钉住“怎样失败”（选中时段条整个消失时也会匹配），原报告“只能因为这一条断言失败”的说法因此说过了头；审查回应后正则同时要求 `Received string:` 一行显示 `Price£0/MWh`。S3 修好之后，棘轮会要求删除这条登记。
   - 不这样改的话，测试会靠 merit order 表里的 £50 显示为绿，等于继续掩盖 R3-01。这是两种做法里更保守的一种。
2. **expanded-workflows:103 和 :118 登记为已知失败（owner P1）。** 计划只列出 :188 需要修。这两条是 UI 按设计改动后留下的过时 spec，不属于本包依赖的 spec；按“只修本包依赖的 spec”处理，没有改写它们。计划中“其余 4/4”的含义不明确；本次实测其余各 spec 的结果是：expanded-workflows 1 通过、2 已登记；result-queries 2/2；comparison-review 1/1；evidence-isolation 1/1；castle-101 在 UI-only 下 4 条全部 skip。
3. **network-redispatch 的计数。** 当前文件共有 22 个测试（有两处 for 循环生成的测试），实测 19 通过、3 个已登记失败。计划写的“≥16/19”是旧计数；`min_passed` 设为 19，比计划更严。原 :710 现在位于 :712，因为 :697 的修正多了 2 行注释。
4. **7 个离线 spec 的选择。** 计划没有逐一列名。选了 market-visibility、network-redispatch、expanded-workflows、castle-101，以及 result-queries、comparison-review、evidence-isolation：后三个都完全用 route mock，并且自带 UI-only 配置。castle-101 需要真实服务，在 UI-only 下 skip（计划要求的是缺包时 skip，这里多了一个 UI-only 条件，并写明了原因）。
5. **S2 只做到生成器、夹具和 Python 测试。** `marketTypes.ts`、编译期穷举和 ui-contract-keys 这些 TS 侧内容不在 M0。真实 Run 使用 golden C3 的冻结项目，而不是会变的课程模板，这样夹具不会随模板漂移。
6. **没有生成 run summary / status.json 夹具。** `build_run_summary` 依赖 model_runner 写出的 `status.json`，`run_project_application` 不产出这个文件。S5/S9 需要时再扩展生成器（见第 6 节）。
7. **夹具预算由 200 KB 提高到 256 KB（第二轮审查回应，待集成者批准）。** 计划 4.9 S2 写的是“夹具合计 ≤200 KB”。M0 的夹具已用 193,585 字节，几乎全部是真实 C3 Run 按 UI 实际请求返回的载荷（value-101-day 的 dispatch-half-hour 54 KB、periods 32 KB、auction-ahead 29 KB、orders 16.5 KB）。S3/S4 会给每个 flow 加 `role`、给价格加 `price_basis`，估计增加 3–9 KB（190 个 flow 行、118 个价格字段），在 200 KB 下 M2 必然失败。可行的“腾空间”办法都会让夹具不再是 API 实际发送的内容：缩小窗口或行数会偏离 UI 的请求参数；把浮点数截到 12 位有效数字只能省约 3.4 KB。所以保留真实载荷、提高预算，常量由测试钉住（再提高必须改测试，可见可审）。集成者如不同意，只需把 `SIZE_BUDGET_BYTES` 和该测试改回 200,000，并在 S3/S4 中决定削减哪个真实夹具。
8. **toy-v8 改形以复现计划的手算 oracle（第二轮审查回应）。** 为使日 bucket 恰为 CCGT 32、onshore 8、accepted supply 40、需求加权价格 55.0，toy-v8 不再包含 battery 放电和 interconnector 的 final_dispatch 行（staged 写入器只写 final_dispatch，计划的 oracle 只有两种技术）。v8 的储能放电与进口覆盖因此只剩 toy-v7 与真实 Run（C3 无 v8 账本）。
