## 2 各步骤要点

### S1 复现
R1 G4-01（停用 A → 安装同命名空间的 B → 启用 A 会写盘）、R2 G4-02（一个外部模块导入失败使整个注册表失败）、R3 坏 hook 使无关草稿的 presets 失败、R4 停用后 `sys.modules` 残留、R5 安装回滚后 `sys.path` 残留、R6 schema 漂移的扩展无法停用。去掉装饰器逐条运行，六条都因预期原因失败；之后各步骤逐条转绿（S2：R1/R4/R5/R6；S3：R2/R3）。

### S2 事务卫生（单独即可阻止 G4-01 落盘）
- `gridform_core/module_quarantine.py`：`MODULE_LIFECYCLE_LOCK`（进程内唯一 RLock）；`ModuleQuarantinedError` 继承 `ContractError`（因而仍是 ValueError，`code` 按实例设置，worker 记录失败时 `public_failure` 直接得到该码）。没有改 `errors.py`。
- 四个库函数（安装/启停 × 模块/扩展）都在锁内执行。
- `runtime_paths.purge_source_root`：清除从某源码根加载的全部模块和该 sys.path 项；停用模块与安装回滚都调用。
- `_namespace_owner` 读内置扩展与 `modules/extensions/*.json` 原始 JSON，找出真正占用者，安装与启用都在写盘前报 `GF_EXTENSION_NAMESPACE_COLLISION` 并点名（G4-01 报 g4-ns-b）；剩余的 `ExtensionRegistry` ValueError 包成 `GF_EXTENSION_REGISTRY_CONFLICT`。
- `_raw_extension_records` 不解析清单：漂移扩展可停用；升级的迁移检查读取保留清单的原始 `state_schema_version`，当前版本被隔离也不能绕过（清单不可读时报 `GF_EXTENSION_INSTALL_STATE`）；内置冲突改按内置扩展 ID 判断。
- `set_module_enabled` 失败时按原字节恢复记录和活动清单。顺带发现：重新启用以前之所以能成功，是因为 `sys.modules` 残留（R4）；`workspace_registry` 会把未启用的源码根移出 sys.path，所以现在在它之后再放入待启用的源码根。

### S3 两遍隔离
- 第一遍逐文件解析并统计 ID/命名空间（解析失败的文件只要有 id 也计入）；与内置 ID 相同 → 只隔离外部条目（`shadows_registered=True`，不构成 blocker）；外部之间 ID 重复或命名空间冲突 → 各方全部隔离；与内置命名空间冲突 → 隔离外部条目。
- 第二遍按原顺序逐条注册，捕获 `(Exception, SystemExit)`。`validate_manifest` 的导入失败改报根因 “failed to import: Type: msg”（`ExternalImportError`，ValueError 子类）。
- 负缓存键为（清单路径、清单 sha256、`tuple(sys.path)`），`clear_negative_caches()`（rescan）清空。
- 隔离条目 `QuarantinedEntry`：kind、相对 `modules/` 的清单文件、id、码、原始异常类型、去路径的消息（数据目录换成 `<modules>`、家目录换成 `~`）、离线修复命令。
- hook：`hook_source_identity` 捕获任意异常，写负缓存与运行期 hook 隔离表，抛 `ExtensionHookImportError`（`GF_EXTENSION_HOOK_IMPORT`，ValueError 子类）。
- `strict=True` 时有隔离即抛 `GF_MODULE_QUARANTINED`；`psm_entrypoint_scan.py`、`run_prompt17b_gate.py`、`run_prompt107_production_gate.py` 与 `module_conformance` CLI 用 strict（CLI 另有 `--allow-quarantine`）。`verify_native_install.py:41`、`sign_install_gb_zonal_pack.py:29` 保持默认：它们在终端用户的数据目录上运行，一个无关的坏模块不应让原生安装校验或数据包签名失败。
- `module_conformance` 对外部构造函数也捕获 SystemExit。

### S4 写后两层校验
- 进程内：从磁盘重建注册表，目标 ID 必须注册，且不得出现写前没有的隔离条目。
- 子进程探针：`python -m gridform_core.module_recovery verify --report`，参数取自 `backend.lifecycle.python_argv.isolated_python_argv`，`-s` 规则与 worker 相同（`match_parent_user_site`），cwd 为源码根，继承环境（另设 `VALUE_DATA_HOME`、新的 pycache prefix），独立进程组；超时（默认 120 s）杀掉本函数自己启动的进程组并回收，报 `GF_MODULE_PROBE_TIMEOUT`；其他失败报 `GF_MODULE_PROBE_FAILED`。报告写文件而不读 stdout，外部代码的打印不会干扰。
- 任一层拒绝都在原事务内抛出，原有回滚逐字节恢复；安装失败时还删除本次新建的空 `<id>/` 目录。停用不做写后校验。已有坏模块 C 不妨碍安装其他模块（只比较新出现的隔离条目）。
- 实测每次安装/启用多 1–2 s。

### S6 server
- 四个生命周期端点与两个上传端点：在锁内执行“库函数 + 刷新”；错误经 `map_request_exception` 按 `ERROR_CODE_STATUS` 映射（冲突 409、探针超时 504、目录 stale 503，表外 400），响应体带 `error_code`（携带隔离条目时附 `quarantine`）。
- pending runs：存在活动 Run（queued/snapshotting/running/cancel_requested）时返回 409 `GF_MODULE_LIFECYCLE_RUNS_PENDING`，JSON 体 `{"confirm_pending_runs": true}` 或上传请求头 `X-VALUE-Confirm-Pending-Runs: acknowledged` 确认后执行。
- 被隔离的模块/扩展即使有 Study 引用也可停用，只有引用它的活动 Run 会阻止（Q3）。
- 刷新失败：保留旧目录，生命周期响应 200 并带 `catalog_stale` 与警告，health degraded（`GF_MODULE_CATALOG_STALE`），启动 Run 返回 503；`POST /api/modules/rescan` 清负缓存并重建，成功即解除。
- `/api/health`：无会话时只有 `status` 和 `degraded_reasons:[{code,count}]`（无 ID、无路径）；有会话时另含 kind/id/文件/码/异常类型（无消息）。`/api/workspace`、`/api/modules`、`/api/extensions` 增加 `module_quarantine`。
- start-run 中原先无码的回答补上 `error_code`（运行策略、zonal 数据包、修订身份、preflight 拒绝、输入快照）；执行归档遇到损坏的安装记录报 `GF_EXECUTION_ARCHIVE_MODULE_RECORD` 并给出相对路径与修复命令。
- `main()`：在 C2 位置重读目录，有隔离条目时只按码打印一行 “VALUE started degraded: …”。
- `test_lock_order` 新增 50 次启停模块 × 50 次启动 Run 的双线程交错，30 s 内完成，锁序无违例。

## 4 应用的决策

- Q3（附表 P0-2）：被引用的隔离条目允许停用，只阻止引用它的活动 Run。
- P0-2 Q1/Q5：冲突各方全部隔离，不设隐式赢家；与内置冲突只隔离外部条目。
- P0-2 Q2：只有启用状态的扩展占用命名空间（`_namespace_owner` 只读活动清单）。
- P0-2 Q4：存在无关隔离条目时新 Run 只警告并留证据（`checks.module_quarantine`）；doctoral 口径的外部代码白名单由 X0 读取 `checks.external_code` 实现（Q3/Q7）。
- P0-2 Q6：修好后用新 ID 发布，同一 ID 不可重装（文档写明）。
- P0-2 Q8：hook 导入失败为运行期隔离并负缓存；启动期子进程探测留 P1。
- P0-2 Q9：有未结束的 Run 时生命周期变更返回 409，确认后执行。
- C1/C3/C4/C5/C6/C14/C27：错误码表接入 `map_request_exception`；health 计数字段并入统一载荷；探针参数取自 `python_argv`；worker 失败经 `record_run_failure`；持有模块锁时不申请 Study 锁并有交错测试；新 HTTP 测试全部用 `local_api_harness`；DATASET_SLOTS 内容哈希常量。
- 两轨通用，不受口径控制；不改 `application.py`，不改 `scheme_c_execution_identity` 覆盖的文件。

## 5 偏差

1. **目录快照在 server 导入时构建一次**（C2 写的是 `main()` 中 `get_catalog_snapshot(refresh=True)`）。server 有约 40 处以模块全局名使用 `MODULE_REGISTRY`/`MODULES`，模块内的全局名查找不经过 PEP 562，测试与脚本也直接读写这些全局；改成函数访问的改动面过大。现在导入时构建的是已隔离的快照（外部故障不再致命），`main()` 在 C2 位置重读同一份缓存并输出降级提示，不重复构建。代价：第二个后端在以 exit 3 退出前也会导入一次外部代码。worker 不导入 catalog（S5 的目标不受影响）。
2. **刷新失败时生命周期请求返回 200**（带 `catalog_stale: true` 与警告），而不是错误码。理由：写后两层校验已经通过，变更本身有效，不应让用户以为没改；同时 health 降级、启动 Run 503，直到 rescan 成功。
3. **pending runs 的判定用 `ACTIVE_STATES`**（含 running 与 cancel_requested），比计划正文的 “queued 或 snapshotting” 更保守，与集成修订“改用 ACTIVE_RUN_STATUSES”一致。
4. **错误码表多于计划估计的约 18 个**：`ERROR_CODE_STATUS` 同时登记了既有的冲突类码（如 `GF_MODULE_ID_COLLISION`、`GF_EXTENSION_VERSION_COLLISION`），这些在 HTTP 上从 400 变为 409；新增码见 CHANGELOG。
5. **`ContractError` 的映射**：所有 `ContractError`（类级 code，如 `GF_CONTRACT_001`）现在以自身 code 回答（状态仍为 400），不再统一为 `GF_REQUEST_INVALID`。棘轮无新失败。
