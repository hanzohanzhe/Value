## 2 实现要点

### 2.1 S2：NativeMarketRules（行为不变）

- **`gridform_core/builtin/scheme_c_1000twh/native_market_rules.py`**（在 runtime_compat 之外）。
  - `NativeMarketRules` 是冻结的 dataclass，`sha256` 覆盖全部字段。两套常量：`DOCTORAL`（`native-doctoral-thesis-v1`）与 `CORRECTED`（`native-corrected-v1`），字段取值按计划 4.6 方案第 1 点的表，sha 互不相同。
  - 按 DECISIONS 调整的字段：
    - `realisation_basis`：两套都是 `forecast_thesis`，没有开关（A2：P3-01 不改调度）。
    - 新增 `storage_settlement_basis`：doctoral `thesis_max_bat_price`，corrected `uniform_clearing_price`（A8）。
    - `operating_cost_basis`：两套相同（P5-06 是两轨都修的 universal 账目修正，S4 会同时改两套），本步取值 `scheme_c_retained_v0`，如实描述现状。
  - 每个可切换字段对应一个 profile_gated correction id（`FIELD_CORRECTIONS`，前缀 `p06.`）。`rules_for_methodology(methodology)` 逐字段调用 `ResolvedMethodology.enabled(<id>)`（C15），不比较口径 id。
  - **这些 id 本步一律列在 `PENDING_CORRECTION_IDS` 中，尚未写入 `corrections/p06.json`**：待定开关在任何口径下都取 doctoral 值，所以两个口径本步都解析为 `DOCTORAL`，行为不变。不在待定集合中、目录里也没有的 id 抛 `UnknownCorrectionError`（拼写错误 fail-closed）。只开启部分开关时得到 `native-partial-<sha12>`。测试强制“待定集合与目录不相交”，因此后续步骤注册某个 id 时必须同时把它移出待定集合。
  - `active_rules(explicit, runtime)`：显式参数 > `runtime.market_rules` > `SchemeCModuleRuntime`（参考路径）取 DOCTORAL > 无 runtime 取 DOCTORAL；其他已配置但缺少规则的 runtime 抛 RuntimeError；类型不对抛 TypeError。
  - `storage_bid_basis_source(obj)`：只有类型**恰好**为 `DynamicAnnualStorageCost` 的对象记为 `rule_set`，其子类（user formula）、legacy tariff、外部模块都记为 `module_defined`。
  - `market_rule_set_record(...)`：生成 `market_rule_set` 记录（规则集 id、sha、全部字段、开关与 correction id 对照、待定开关、存储模块 id、报价基准归属、内核树 sha、VoLL）。
- **`scheme_c_native_psm.py`**：`run` 中由 `current_methodology()` 推出规则集，构造 `SimpleNamespace(storage_cost=…, market_rules=…, realisation_log=…)`（`realisation_log` 是 S3 加的）。`_StorageRuntime` 增加 `market_rules` 与 `bid_basis_sources`（按电池类型记录）。该文件是 CRLF/LF 混合行尾，编辑时逐行保留了原行尾。
- **内核**：新增 `_active_rules(market_rules=None)`（读取 `module_context._runtime`，逻辑在 `native_market_rules.active_rules`）；`run_simulation` 增加关键字参数 `market_rules=None`，开头解析一次规则集。本步没有任何出清步骤读取它。
- **harness**（`tests/native_reproduction_harness.py`）：`_loop_environment` 默认在 runtime 中放入 `DOCTORAL`（M0-P0-6-S1 报告第 6 节预告过的做法），调用方仍可经 `runtime_attributes` 覆盖。冻结循环不调用 `_active_rules`，不受影响。

### 2.2 S3：抽出 realise_period（纯重构），确立恒等式

- **内核**：把 `run_simulation` 中“`if real_demand < forecast_demands[period]` … 两个分支直到 `excess_energy_final_dict[period] = excess_energy`”整段（HEAD 2733-2802，本次编辑前为 2745-2813）抽成模块级函数 `realise_period(...)`：
  - 市场调用（`curtailment_market_bidding` / `balancing_market_bidding`）和 `set_real_gen_energy(0)` 循环逐字搬入，返回 `PeriodRealisation`。
  - `run_simulation` 按 HEAD 原样追加各列表；类型也保持不变，例如削减分支追加的 `balancing_fee`、`purchase_fee`、`blackout` 是整数 `0`，平衡分支追加的 `curtailment_fee`、`curtailed_energy` 是整数 `0`。这一点重要，因为 trace 写出器会把它们序列化。
  - 跨期残留 `total_storage_fee_balance` 在削减分支中原样带回（doctoral 冻结行为，S5 才按规则集改）。
  - 规则集作为参数传入，本步不读取。
- **`native_realisation.py`**（runtime_compat 之外）：
  - `PeriodRealisation`；
  - `RealisationLog`：numpy 数组，不持有对象引用，单位为内核功率单位（MW，乘期长得 MWh）。列为 branch、预测需求、实际需求、充电、excess、削减、缺电、柔性负荷、出口。
  - `active_realisation_log`：用 runtime 提供的日志（每次运行重新开始），没有就用私有日志。
- **`energy_balance_contract.py`**（C19，恒等式只在这里实现）：
  - 新边界 `native_corrected_full_node_v1`：r = S + B − D − C − E − X − XS。在 corrected 列语义下，S = 非储能、非联络线来源的毛出力（VRE 含被消耗的盈余）+ 进口 + 储能放电；XS = 非 VRE spill。
  - 辅助函数：`native_node_flows(...)` 由来源项构造 `PeriodFlows`；`native_corrected_residual`；逐 VRE 恒等式 `vre_source_residual`（可用 = 已接受 + 被消耗盈余 + 弃电）。
  - `boundary_residual` 已分派到新边界；`envelope_bounds` 对新边界为 (XS, XS)。
  - `BOUNDARY_REGISTRY` 新增条目 (`value-bid-at-cost-psm`，≥6.0.0，`native-corrected-v1`)。规则集 id 只定义在 contract 中，`native_market_rules.CORRECTED_RULE_SET_ID` 引用它。
  - oracle 没有改动；内核按规则集声明边界属于 S5。

## 5 偏差

1. **P0-6 的修正本步不写入方法学目录**。计划写的是“规则集以 X0 修正目录中的开关为准”。我把开关与 correction id 的对照建好了，但目录要求每条 profile_gated 修正都带 trigger_fixture（同一玩具算例，冻结口径给旧值、修正口径给新值），而 S2 是行为不变的步骤，给不出这样的算例。现在就登记还会改变 corrected 的 `applied_corrections_sha256`，把一个空操作说成方法变化，触发 Study 迁移确认（Q13）。因此本步所有开关都列为待定，两个口径都解析为 DOCTORAL。S5–S10 每实现一个开关，就在同一提交中写入 `corrections/p06.json`（带 trigger fixture），并移出 `PENDING_CORRECTION_IDS`；测试会强制这一点。计划中的“两套规则集 sha 不同”针对的是两套目标常量，已满足。
2. **`market_rule_set` 记录本步只提供生成函数，不写入 extensions 和账本 metadata**。写入账本 metadata 会改变 market.sqlite，与 S2/S3 的“48 期逐字节一致”验收冲突。写入时机留给 S5（内核按规则集声明边界时）或 S11（身份步骤）。
3. **`_StorageRuntime` 只记录报价基准归属，不配置报价基准**。`DynamicAnnualStorageCost` 还没有对应属性，配置属于 S10。
4. **preflight.py 未改**。计划 S2 文件栏列了 preflight.py:227，但 S2 没有需要预检的行为；`GF_STAGED_DWELL_NOT_TRACKED` 属于 S10。
5. **core.md（drafts）本步未写**。`docs/methodology/drafts/0.4/` 还不存在；按计划，它由 X0 创建并加入发布排除清单。恒等式的定义已写在 `energy_balance_contract.py` 的模块文档中，方法学草稿留给 S11 的文档步骤。
6. **RealisationLog 只记录 HEAD 内核现有的量**（分支、F、R、充电、excess、削减、缺电、柔性负荷、出口）。被消耗的 VRE 盈余、非 VRE spill 这类逐来源量要等 S5 的盈余记账才有，因此本步只用手算验证新恒等式，还没有拿它评估内核输出。
7. 新边界的注册表条目从 6.0.0 起才生效（版本台账中 P0-6 的目标版本）。doctoral 规则集在 6.0.0 及以后的条目由 S5 补充，到时内核才开始声明边界。
