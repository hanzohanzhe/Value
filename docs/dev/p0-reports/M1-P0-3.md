## 2 各步骤要点

### S1 轻量包
- `file_locks`：POSIX `flock`、Windows `msvcrt.locking`（第 1 字节）；按线程的重入检测（立即抛 `LockReentryError`）；`LockTimeout` 继承 `TimeoutError`（即 `OSError`）；锁文件从不 unlink、不被子进程继承；`probe_lock` 不创建文件或目录。
- `atomic_io`：`mkstemp` 唯一临时名 + fsync + `os.replace`；目标目录不存在时报错而不创建（迟到写入不会把已移走的 Run 目录"复活"）；Windows 终态写入重试 10 s。
- `states`：唯一状态表。新增 `queued/running/snapshotting → cancelled`（取消改为请求文件后由 worker 直接记 cancelled）；`failed → cancelled` 仍禁止；`deleting` 只有对账器可用的 `REPAIR_TRANSITIONS`；`unknown` 表示缺失、损坏或不认识的状态。

### S2 单写者 API 与写入方迁移
- `create_status` / `update_status(mutate=, transition=, reason_code=, writer=, legacy_replace=, merge_unknown=, repair=)`：在 `<run>/status.lock` 内重读、合并、原子替换；`mutate` 改 `status` 或 `lifecycle_history` 一律抛错（显式 raise，`python -O` 下同样生效）；每次迁移追加连续 sequence 的历史项（`assert_history_chain`）。
- 迟到写入：worker 写入时 Run 已非活动态 → 不动 status 和任何封存产物，只在根目录写 `late-worker-*.json`，抛 `LateWriteRejected`，worker 以 0 退出。
- 服务端在 worker 持有租约时写活动 Run → `LeaseHeldError`。
- `record_run_failure`/`record_run_cancelled` 拆为两段：先在锁内判迟到，再在锁外写诊断和 failed provenance，最后合并写 status；签名不变（只加可选 `error_code`）。
- worker 的 running/completed 改为对磁盘最新内容做字段合并，application 写入的 `subannual_recovery*`、服务端的 `quota`/`extensions` 都保留（P7-08）。
- 服务端：建目录后立即 `create_status(snapshotting)`，此后每条失败路径都迁到 failed（含意外异常 `GF_RUN_START_FAILED`），不再有看不见的孤儿目录；resume、archive、restore 都是带锁的迁移；cancel 只写一次 `cancel-request.json`，重复 cancel 返回 202 且文件和 status 逐字节不变，`present_run` 显示 `cancel_requested` 并给出 `persisted_status`；服务端所有状态改动在 `RUN_ACTION_LOCKS[run_id]` 下串行。

### S3 轻量 worker 入口
- `python -m backend.worker_entry --run-dir --lease-nonce --project --run --mode`。第一阶段只用标准库：拿 `worker.lock`（2 s 内拿不到 → exit 75），核对 `worker.json` 中的 nonce 与 `queued` 状态（不符 → 不写任何东西 exit 0），写 `worker-lease.json`，装 SIGTERM/SIGHUP/SIGBREAK 处理器（抛 `WorkerTerminated`，BaseException）。第二阶段在 try 内 `from backend import model_runner`，任何导入失败记为 `GF_WORKER_IMPORT_FAILED`。
- 退出码：0 完成/取消/迟到；1 失败；128+n 信号（SIGTERM 143，`GF_WORKER_TERMINATED`）；130 KeyboardInterrupt。model_runner 的模块级名字保持不变。

### S4 监督、回收、对账、单例
- `spawn_worker`：先写 `worker.json` v2（含 nonce），再在独立 session/进程组中启动 worker（Q4：停止后端的进程组不会杀 worker），记录 pid、/proc 起始时间、boot id；不在 status 锁内 spawn。
- 回收线程 `proc.wait()`（无僵尸），写 `worker-exit.json`，活动 Run 转 failed（有取消请求则 cancelled），`GF_WORKER_EXITED {returncode, signal}`。
- 5 s tick 只处理孤儿：租约被持有 = 存活（新后端接管监督）；租约空闲 = `GF_WORKER_LOST`；Windows 需相隔 5 s 两次空闲探测；v2 worker 生成 30 s 内仍视为 starting；v1 worker 在 Linux 上按 /proc argv 判断，其他平台为 unverifiable。
- `reconcile_all` 在绑定端口前同步运行，不哈希、不遍历产物；修复旧版遗留的 `deleting`；failed provenance 交后台 sealer。`VALUE_RUN_RECONCILER=observe` 只报告不改写。
- mark-lost：`POST /api/runs/<id>/mark-lost {confirm_run_id}`，确认门（完整 run ID）+ 安静期门（15 分钟无文件变化）；租约被持有时 409。
- `main()` 顺序：state layout → `.backend.lock`（拿不到 → exit 3）→ default pack → reconcile_all（含 S6 的启动清理）→ workbench → bind → 监督/sealer 线程 → serve；SIGTERM/SIGHUP 干净退出，并打印仍在后台运行的 Run。
- 发现：worker 的 `-s` 会改变执行身份中的 `no_user_site`，开发方式启动（不带 `-s`）的后端会让 worker 因"执行身份变化"失败；因此 worker 镜像后端自身的 `no_user_site`（见偏差 1）。

### S9 启动器字节码隔离
- `desktop_value.py`：运行时探针、教学数据包安装、后端启动都用 `isolated_python_argv`（`-B -s -X pycache_prefix=<每个启动器进程新建的空目录>`）；`clean_environment` 设置 `PYTHONPYCACHEPREFIX`。
- 在此之后才放宽校验：installed 模式下 `__pycache__` 内的 `.pyc/.pyo` 归为 stray，不计入 unknown；其余未知文件（包括 `__pycache__` 外的 .pyc、`__pycache__` 内的非字节码）照旧拒绝。start 在 supervisor 锁内把 stray 移到 `state/quarantine/bytecode-<时间>/`（只读安装保留原位并提示）；diagnose 分目录统计并新增 `--repair-bytecode`。
- `local_value.py`：API 用隔离 argv 和新的 `PYTHONPYCACHEPREFIX`；`stop` 输出 `background_runs`。full-local 三平台 start/diagnose/install 脚本给控制解释器设置新的前缀。

### S7 HTTP 异常边界

## 6 偏差

1. `worker_python_argv` 增加可选参数 `match_parent_user_site`（默认 False，约定接口不变）。原因：`no_user_site` 是执行身份的一部分，worker 带 `-s` 而后端不带时，worker 会以"执行身份变化"失败（scratch 实测）。spawn 时 worker 镜像后端自身的标志；受管启动器总以 `-s` 启动后端，因此安装版 worker 仍带 `-s`。已写入 P0_CONVENTIONS 第 8 节。
2. 入口模块：约定写 `-m backend.worker_entry`，计划写 `backend/lifecycle/worker_entry.py`。两者都提供：实现在 `backend/lifecycle/`，`backend/worker_entry.py` 是薄壳。
3. `tests/local_api_harness.py` 本应由 P0-1 S2 提供。为满足 C14（新 HTTP 测试必须用它），本单元按约定接口实现了最小版本（无令牌时 token 为 None）。P0-1 如在其他 lane 也新建此文件，合并时会出现 add/add 冲突，应以 P0-1 版本为准并保持接口。
4. `tests/test_lock_order.py` 由本单元先建，只覆盖 Run 侧锁（STUDY → RUN_ACTION → reservation → status）；`MODULE_LIFECYCLE_LOCK` 与"启停模块 × 启动 Run 各 50 次"的交错测试留给 P0-2。
5. 异常映射表多一条：`UnicodeError`（ValueError 子类）→ 500，表示存储记录损坏而非请求错误。
6. `merge_unknown`：application 的恢复证据写入在 status 缺失或状态不可识别时仍做字段合并（保持 0.6.0a2 行为与 test_zonal_subannual_resume 不变）；计划说只有 record_* 可在遗留态上创建或替换——这里只合并字段、不迁移状态。
7. worker 退出或丢失时，若存在取消请求（文件或旧的 cancel_requested 状态），Run 记为 cancelled，否则 failed（采用审查报告的建议）。
