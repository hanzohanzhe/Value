# VALUE 前端分阶段施工计划

版本 1.0　日期 2026-10-02

本计划把已完成的前端设计落实为可使用的研究流程。第一阶段已经交付；从第二阶段开始，按可验收的功能批次施工。架构师负责需求、接口、科学语义和代码审核，GPT-6.1-sol 负责边界明确的实现。每批只做与改动风险相关的必要验证，不以测试数量作为进度指标。

## 目标与四条路径

产品保留统一的 Study、Run、数据包、模块和扩展体系。四条路径可自由切换，不是权限等级，也无需逐级解锁。

| 路径名称 | 用户最终得到的东西 |
| --- | --- |
| reproduce from existing data | 按声明范围复现的研究、输入与方法身份、可追溯的对照结果 |
| add your new data | 保留方法的新 Study、独立数据包、数据变化说明与对照结果 |
| Edit module | 带版本的模块、契约与必要测试报告、方法差异和结果差异 |
| add new function to VALUE | 带数据契约、模块、验证和结果展示定义的扩展能力 |

第一阶段的四个入口已经可用，但完整引导流程仍需后续施工。短期优先服务复现和换数据的用户，随后建设模块与扩展作者工具。简洁 Read me 与界面功能同步更新。

## 阶段与验收

### 第一阶段 工作区基础 已完成

已交付四入口首页、Read me、导航分组、继续已有研究、冻结 Run 来源栏、链接恢复和基础手机布局。执行状态、契约检查和科学验证分别展示。源码以独立副本和增量包交付，未替换其他任务正在运行的源码。

### 第二阶段 复现与换数据 当前施工

建立“选择基线 → 明确数据变化 → 核对配置 → 保存独立 Study → 检查并运行 → 对比”的流程。先复用已安装数据包和现有数据工作台，不为引导页另建数据编译器。

施工批次 2A：增加统一研究引导页和专用 Study 派生接口。服务器分配新 ID，保留源 Study，记录来源研究、修订、数据包和任务意图。复现路径拒绝已漂移的输入或方法；换数据路径显式选择不同数据包，保留方法、参数覆盖、年份和求解器契约。保存与启动运行分离。

施工批次 2B：绑定预检请求、响应和显示的 Study ID、revision、pack 与运行范围。旧请求晚到、切换研究或更新版本时，不显示上一项研究的通过状态。用户可返回数据工作台安装或检查输入，再回到引导流程。

施工批次 2C：在派生研究的运行页显示来源与下一步，提供基线 Runs 和现有比较功能入口。比较必须先核对范围与变化维度，不把多因素差异自动归因于数据或方法。历史 Run 精确复现与“按当前保存的 Study 配置重跑”分开表达。

验收：用户能从首页创建独立副本，源研究不变，数据/方法变化可见，保存不会启动计算，预检身份正确，运行后能找到基线和比较入口。没有可用基线、缺失数据、旧版本冲突和服务断开均有明确处理入口。完整历史输入恢复及数据包复制/映射增强按真实缺口继续补齐，不冒充已完成。

### 第三阶段 结果查询与页面结构

提取独立的 Study、运行、结果和证据功能模块，减少主页面中的状态耦合。为 SQLite 账本和独立 compact 结果提供只读查询适配，统一带版本的结果响应，保留原来源身份。按年份、时窗和分页读取；科学聚合在服务层完成。

验收：同一指标在来源允许的范围内语义一致；缺失维度明确不可用；长结果无需整份载入浏览器；图表可追溯输入、方法和范围。先选择一种结果族完成端到端适配，再扩展，不一次重写全部结果系统。

### 第四阶段 模块作者工作台

为 Edit module 增加模块槽位与输入输出说明、源码/模板入口、版本对照、兼容性与测试报告，以及受控结果比较。复用现有本地模块开发、打包与安装机制。有限公式编辑和完整 Python 模块编辑保持清晰边界。

验收：作者可以定位要改的模块，知道状态读写责任，安装新版本并在新 Study 中选择；不兼容的模块有具体原因；旧 Study 与旧 Run 仍可追溯。浏览器中任意 Python 执行环境不属于本阶段默认范围。

### 第五阶段 新功能开发流程

为 add new function to VALUE 提供扩展提案和脚手架：研究问题、数据 roles、能力声明、生命周期接口、状态责任、模块组合、结果 schema、验证样例与迁移说明。模板和校验来自统一契约，减少文档与实现漂移。

验收：以一个范围有限的示范扩展完成声明、验证、安装、Study 组合和结果展示；普通前端仅开放真正可执行的能力。新增物理方法单独做解析算例或必要数值验证，不能以界面可点击代替模型通过。

### 第六阶段 主线集成与发布

把已经验收的前端与服务层改动合入选定发行基线，保留数值补丁、模块版本和历史身份。形成可安装发行包、简洁用户说明、开发者说明和必要运行诊断。

验收：在目标环境完成安装、教学或最小研究、数据接入、一次运行与结果读取、失败恢复入口检查。全仓库类型、云部署与长周期性能只在对应交付范围内验收，未验证项明确列出。工程可执行与科学可发布分别判断。

## 架构决定与主线边界

当前前端工作副本位于 work/value-frontend，第一阶段基于 Value_GoogleCloud_Release/frontend-model 0.6.0-alpha.2。2026-10-01 的 GBP1 数值政策另有独立源码和运行；已核对其 HTTP 服务基线，不能把数值补丁里的旧 app/page.tsx 整页覆盖到新前端。

本轮以稳定接口推进第二阶段，主动记录与最新科学源码的集成差异。运行中的源码、账本和检查点保持原身份；任何数值政策或物理算法修改均另立范围与验证。恢复粒度必须根据实际 Run 能力展示，不将某一分支的月度恢复描述为全部版本能力。

派生 Study 必须由服务端执行，只创建新身份，不靠改 name 猜测目标 ID。来源研究修订采用乐观并发检查，防止用户审阅期间基线改变。数据包和网络覆盖包分开显示；换基础数据不隐式替换网络包。复现必须核对现存数据与记录身份，不能把可变工作区当作历史输入。

第三和第五阶段再推进模型服务层结构优化：统一查询响应、模块契约、状态所有权与扩展接口。四条社区路径共用现有 registry、预检、年度执行和结果账本，避免出现另一套简化计算逻辑。

## 分工与施工节奏

| 职责 | 架构师 | GPT-6.1-sol 施工员 |
| --- | --- | --- |
| 需求与范围 | 拆解用户流程、确定验收条件和科学边界 | 报告实现缺口与歧义 |
| 接口和状态 | 定义数据契约、身份和错误处理 | 按约定实现组件、服务、文档 |
| 代码变更 | 审核关键逻辑、集成与冲突处理 | 在指定文件范围施工，避免互相覆盖 |
| 验证 | 决定风险对应测试，审阅证据 | 执行指定必要测试，修复实际失败 |
| 交付 | 审核成品、更新进度与剩余范围 | 提供变更说明、命令与结果 |

每批先确定“输入、输出、允许修改的文件、禁止改变的语义、验收方式”，再分派实现。相互独立的组件可并行；共享主文件和接口由架构师统一集成。交付前检查异步竞态、版本来源、错误状态、保存与运行边界以及用户操作是否完整。满足本批验收后继续下一批，常规可逆实现无需重复请求批准。

## 必要测试政策

| 改动风险 | 最小验证 | 不默认执行 |
| --- | --- | --- |
| 文案与局部样式 | 相关页面视觉检查，必要的窄屏检查 | 全量单元测试、模型运行 |
| 组件状态与导航 | 一条正常路径和真正相关的错误/返回场景 | 多浏览器多分辨率穷举 |
| 身份、派生或数据写入 | 来源保留、旧版本拒绝、错误不落半成品的定向测试 | 无关结果图表测试 |
| 异步请求 | 一次延迟响应/切换上下文检查 | 反复刷新刷通过率 |
| API 或构建集成 | 改动相关测试，加一轮类型检查和生产构建 | 每改一行就重复全量检查 |
| 科学算法或状态推进 | 受影响数值算例、守恒与必要跨年回归 | 因纯前端改动重跑十年模型 |

第二阶段集中验证四件事：独立副本保留配置与来源；换数据不改方法；旧来源和旧预检被拒绝；保存不会启动 Run。浏览器只走复现、换数据和关键异常流程。一次通过后，只有新改动、失败或明确未解风险才扩测或重跑。文档只检查内容完整和最终版排版，不为版式写自动化测试。

## 交付与完成定义

各批交付可运行源码、变更清单、必要测试结果和简短使用说明；需要跨目录集成时附基线身份与补丁。计划和施工记录分别维护：本计划说明要做什么，施工记录说明已做成什么。

完成一个阶段意味着其用户流程与验收条件均满足，而不是入口已出现或测试数量足够。遇到科学定义、新权限或不可逆外部发布等新的实质决定时再交给用户；普通实现选择由架构师处理。第二阶段当前进入 2A 和 2B 的实现，后续按上述依赖顺序推进。
